# 정리

실험 2에서 난 `1`, `1.0`, `True`가 하나의 키로 합쳐지지라고 예상을 못했다. \
그러나 그런 이유가 있다면 실제로 저 3개의 값이 hash값이 동일할 거라는 예상을 할 수 있다. \
`==`연산을 내부적으로 이용한다면 기존에 이미 있는 key의 hash값이 있다고 판단하여 덮어쓰기 했을 것이다.

실험 4에서 `set(edges)`와 `frozenset`의 차이는 단순하다. \
edges를 직접 set에 넣었을 때는 원소가 tuple형태로 들어가 hash될 것이고, 그럼 순서 정보가 보존된다. \
반대로 frozenset의 경우는 그러한 정보가 사라졌다. 간단하게 : `frozenset((1, 2)) == frozenset((2, 1))`이렇게 될 것이다. \
set의 원소가 될 수 있는 조건은 hashable할 것.

실험 6의 배율 결과를 본다면 `dict`, `set`중 하나의 자료구조, 그마저도 key-value쌍이 필요 없다면 `set`을 활용하는 것이 좋아보인다.

claude의 보충 설명: 1“del이 list 안의 객체를 파괴한다”는 부정확합니다.
del a[::2]는 객체를 파괴하는 것이 아니라, list가 들고 있는 참조(이름표)를 떼어내는 연산입니다.
또 하나 짚자면, 예상하신 “slice된 객체만 사라진다”는 del a[::2]가 아니라 del a[::2]를 표현식으로 a[::2]만 평가했을 때 일어나는 일입니다. a[::2]를 단독으로 쓰면 새 list가 만들어지지만, del이나 대입의 왼쪽에 오면 원본 list의 __delitem__/__setitem__이 호출됩니다. 같은 문법 모양인데 위치에 따라 동작이 달라지는 지점입니다.

```python
[0, 1, 'x', 5, 6, 7, 8, 9]
# 이것은 a[2:5] = ['x']의 결과이다. 나는 broadcast될 것이라고도 생각했지만, 결과는 진짜 그 부분만 'x'로 바뀌어 짧아졌다.
[0, 'i', 'j', 1, 'x', 5, 6, 7, 8, 9]
# a[1:1]의 경우는 실질적으로 insert 처럼 작동하였다.
['i', 1, 5, 7, 9]
# del a[::2]를 진행하면 생기는 결과, 난 단순히 slice된 a[::2]객체 자체만 shallow하게 사라져 기존 list에 변함이 없을 것이라 생각했다.
```
